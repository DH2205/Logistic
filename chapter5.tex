\section{Experimental Setup and Evaluation Methodology}

In order to evaluate the performance, architectural resilience, and user-centricity of the developed LogiShop platform, a structured empirical study was conducted in this chapter. The main objective of this chapter is to assess how well the system fills the research gaps uncovered in Chapter 2, especially in terms of geopolitical and structural route disruptions, multi-carrier data normalization, and cost-impact computing.

The evaluation process has been based on quantitative performance benchmarks and qualitative feature tests. Quantitatively, route calculation and API synchronization data pipelines were tested using simulated request loads to test response times as well as system resource overhead. Qualitatively, features were compared against older industry models. A set of operational parameters, contract base pricing figures, and delivery route vectors were obtained from anonymized telemetry data provided by VN Express International Delivery Company Limited (VNEXID) to bridge the gap between theoretical algorithm implementation and commercial constraint analysis.

\section{Algorithmic Evaluation and Disruption Handling}

The core mathematical engine behind LogiShop's resilience is the dynamic graph-reweighting framework formalized in Algorithm \ref{alg:disruption-weighting}. To validate its efficiency, the system was subjected to a simulated geopolitical crisis scenario mirroring trans-Eurasian airspace closures. A standard test route from Tan Son Nhat International Airport (SGN) to John F. Kennedy International Airport (JFK) was mapped onto the graph network $G=(V,E)$.

Rather than failing or producing a breaking exception, the LogiShop DSS re-traversed the active graph. It automatically discarded the compromised northern edges and generated a southern bypass trajectory via Singapore (SIN) and Dubai (DXB). It proactively bypassed the high-risk zone.

\subsection{Disruption Cost-Impact Reconciliation}

To maintain rigorous accounting consistency across operational routing tiers, a clear distinction must be established between localized edge-weight penalties and macro-level contractual penalties. The value of \$26.53 USD computed dynamically in Table 4.7 represents the isolated, operational overhead variance ($C_{\text{operational\_overhead}}$) incurred by the transit asset while maneuvering through the active US-Iran disruption corridor. 

This algorithmic output serves exclusively as an edge-weight penalty variable within the real-time pathfinding layer. Conversely, the baseline structural contract penalty for late-door delivery, defined as a macro-economic parameter in Section 5.4, stands at a flat rate of \$150.00 USD per diem ($P_{\text{contractual}}$). 

Consequently, for an empirical shipment experiencing an operational route latency of $\Delta t = 4.2$ days within the affected sector, the total compounded fiscal liability ($C_{\text{total\_disruption}}$) is formulated as follows:

\begin{equation}
C_{\text{total\_disruption}} = \int_{0}^{t} C_{\text{operational\_overhead}}(\tau) \, d\tau + \left( \lceil \Delta t_{\text{days}} \rceil \times P_{\text{contractual}} \right)
\end{equation}

By isolating the dynamic, micro-level routing cost updates from the flat, macro-level contract milestone fine indicators, the algorithm preserves its optimization sensitivity while accurately scaling to meet total multi-day logistical liabilities in real-world SME environments.

\section{Asynchronous API Performance and Scalability}

A major technical challenge in system implementation was the limit on API rate and how to avoid user interface lag during data fetching. LogiShop pulls telemetry from multiple carrier layers at once so the backend needs to process data atomicity.

To test the boundaries of the system, telemetry ingestion pipelines were stress tested by generating continuous webhook pulses to simulate concurrent data streams. During initial testing, unthrottled concurrent requests rapidly exceeded the traffic levels imposed by the external carrier sandbox environments. This baseline workload resulted in immediate HTTP 429 (Too Many Requests) exceptions. This data bottleneck confirmed that standard, naive polling methods quickly fail under realistic enterprise conditions, as unhandled synchronous request accumulation directly blocked the application event loop and caused noticeable latency propagation to the user dashboard.

When an HTTP 429 exception occurs, the ingestion worker automatically halts immediate retries, logs the exception state without breaking the user's dashboard view, and starts a backoff loop that progressively delays the user’s execution. This programming approach makes sure that even if external APIs are throttling requests, LogiShop can overcome this and keep applications running at a high uptime. It keeps local order data in Supabase secure and responsive, which makes it very scalable for Vietnamese logistics companies.
