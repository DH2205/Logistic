IMPLEMENTATION PROMPT: Add Logistics-Aware Route Scoring System
===============================================================

Project context:
This project is a Next.js + TypeScript logistics web application called LogiShop. The route visualization and rerouting logic are used in TransportationMap. The current rerouting logic uses Dijkstra in thesis/backend/lib/disruption-router.ts and displays the rerouted path in thesis/frontend/components/maps/TransportationMap.tsx.

NOTE ON PATHS: All application code lives under the `thesis/` subdirectory of the repo. Use the exact paths below — there is no top-level `backend/` or `frontend/` directory.

Current problem:
The current route optimization logic is too simple. `edgeWeight` in disruption-router.ts hard-blocks any edge that touches a `high` or `critical` disruption zone (returns Infinity), and otherwise multiplies distance by a severity factor. Dijkstra then always routes from the nearest origin hub to the nearest destination hub. This causes unrealistic behavior: if the destination hub itself is inside a critical zone (e.g. Los Angeles port closure), the algorithm still forces the route to terminate at Los Angeles, producing a path that "returns into" the closed zone. There is no concept of choosing a different gateway when the natural one is unsafe, and no logistics explanation attached to the chosen route.

Goal:
Improve the rerouting system by adding a logistics-aware scoring model. The system should not only find the shortest path, but the safest, most reasonable, and most explainable route under disruption conditions.

Important files (verified paths):
- thesis/backend/lib/disruption-router.ts          (graph, edgeWeight, dijkstra, findReroute)
- thesis/frontend/components/maps/TransportationMap.tsx
- thesis/backend/lib/tracking-reroute-insight.ts
- thesis/backend/lib/geocoding.ts

Existing relevant surface (do not break):
- LOGISTICS_HUBS, RAW_EDGES (exported)
- findReroute(fromLat, fromLng, toLat, toLng, disruptions, options) -> RerouteResult
- RerouteResult { waypoints, totalDistanceKm, blocked, metrics }
- regionToBbox, directRouteBlocked, polylineIntersectsDisruption
- Thesis demo helpers (getThesisS1RerouteWaypoints, DEMO_DISRUPTION, etc.) — leave intact.

Main implementation idea:
Keep Dijkstra, but change the edge weight from simple distance to a logistics score, AND add a gateway-substitution step BEFORE running Dijkstra so the destination hub itself can be swapped when blocked.

Current simplified idea:
edgeWeight = distanceKm * severityMultiplier (or Infinity for high/critical touches)

New desired idea:
edgeScore = distanceKm
          + disruptionPenalty
          + modePenalty
          + gatewayPenalty
          + hubPenalty
          + riskPenalty

Then validate the full route after Dijkstra returns it.

1. Add disruption type support

Extend the disruption model from only `severity` to also carry a `type`:

  severity: 'low' | 'medium' | 'high' | 'critical'   (already exists)
  type:     'port_closure' | 'conflict_zone' | 'storm' | 'congestion'
          | 'airspace_closure' | 'sea_lane_closure'   (NEW, optional)

Backward compatibility is mandatory. Old disruptions without `type` must still work. Implement `inferDisruptionType(disruption)` which falls back to keyword matching on `name`/`description`:

- "port closure", "closed port", "closing port" -> port_closure
- "war", "conflict", "attack"                   -> conflict_zone
- "storm", "typhoon", "hurricane"               -> storm
- "congestion", "delay"                         -> congestion
- "airspace"                                    -> airspace_closure
- "sea lane", "canal", "strait"                 -> sea_lane_closure
- default                                       -> conflict_zone (current behavior)


2. Implement route scoring rules

Base:
- distanceKm is always included.

Severity:
- low:      small additive penalty
- medium:   medium additive penalty
- high:     strong penalty or hard block depending on type (see below)
- critical: hard block for serious types

NOTE: The current code hard-blocks BOTH `high` and `critical` (line ~714 in disruption-router.ts). The new model should make `high` block ONLY for serious types (port_closure, conflict_zone, sea_lane_closure, airspace_closure when mode matches) and otherwise penalize. Confirm this is the intended loosening before shipping — it changes behavior for existing `high`-severity disruptions.

Disruption type behavior:
- port_closure:
  - block the affected hub (mark hub as unusable)
  - block edges entering/leaving that hub
  - do not block unrelated route segments outside the port area
- conflict_zone:
  - block hubs inside the bbox
  - block edges whose arc crosses the bbox for high/critical
- storm:
  - penalize sea and air edges crossing the zone
  - block only if critical
- congestion:
  - add penalty; block only if critical
- airspace_closure:
  - block air edges crossing the zone
  - allow sea and land alternatives
- sea_lane_closure:
  - block sea edges crossing the zone
  - allow air and land alternatives


3. Add destination/gateway safety detection

Before running Dijkstra, detect whether the destination hub (the result of `findNearestHub(toLat, toLng)`) is blocked.

If destination hub is inside a critical/port_closure/conflict_zone disruption:
- mark originalGateway as blocked
- generate candidate safe gateways (see #4)
- run Dijkstra from origin hub to each candidate
- choose the best safe route (see #8)

If destination hub is fine, behave like today: single Dijkstra to that hub.

5. Add gateway suitability scoring

Implement:

  calculateGatewayScore(originalDestination, candidateGateway, disruptions, context)

Suggested factors:
- distance from original destination (haversine)
- same-coast preference (group US_LA/US_LGB/US_OAK/US_SEA/US_VAN as West, US_NY/US_SAV/US_MIA as East, US_HOU as Gulf, US_CH as inland)
- gateway type (seaport > airport > storage for sea-borne origins; reverse for air)
- whether candidate is inside any active disruption (Infinity if yes)
- whether the route to the candidate would itself cross a disruption (added later by validateRoute)
- whether candidate is a realistic international entry point (inland hubs get a high penalty)

Example scoring:
- same-coast safe gateway: low penalty
- opposite-coast gateway: medium/high penalty
- inland hub as entry point: high penalty
- blocked gateway: Infinity


6. Update edge scoring

Replace or extend `edgeWeight()` with:

  calculateEdgeScore(edge, hubById, disruptions, context):
    { score: number; blocked: boolean; reasons: string[] }

Example:
  { score: 9300, blocked: false, reasons: ["Base distance 9300 km"] }
  { score: Infinity, blocked: true,
    reasons: ["Edge enters critical Los Angeles port closure"] }

Dijkstra still consumes only `score`, but `reasons` is collected for explanation. Keep the function pure (no I/O, no console.log).


7. Add route validation

After Dijkstra returns a path, validate it:

  validateRoute(waypoints, disruptions, context):
    { ok: boolean; failures: string[] }

Checks:
- no waypoint is inside a critical blocked zone
- no segment crosses a critical conflict_zone
- final gateway is not blocked
- route does not re-enter the same closed destination zone
- total distance is finite and route has >= 2 waypoints
- route distance is not excessively longer than the direct great-circle without reason (e.g. cap at 4x direct distance unless the only feasible path)

If validation fails:
- reject the route
- try next candidate gateway
- if all fail, return status `"no_safe_route"`


8. Add candidate route ranking

When destination is blocked or multiple gateways are possible:
- generate candidate gateways via generateGatewayCandidates(destination, disruptions, hubs)
- run Dijkstra to each candidate
- validate each route
- compute final routeScore:
    routeScore = totalEdgeScore
               + destinationPenalty
               + gatewayPenalty
               + detourPenalty
               + modeSwitchPenalty
- choose lowest routeScore that passes validation

12. Implementation guidance

- Do not remove Dijkstra.
- Do not put scoring logic inside TransportationMap.
- Keep routing/scoring logic in thesis/backend/lib/disruption-router.ts, or extract to a new helper file thesis/backend/lib/logistics-route-scoring.ts and import it.
- Keep the frontend focused on display and explanation.
- Type additions must be backward compatible — old disruptions without `type` still work via inferDisruptionType.
- Use conservative default scoring constants exported as named consts at the top of the module so they are easy to tune.
- Preserve existing thesis demo functions (getThesisS1RerouteWaypoints, DEMO_DISRUPTION, qualifiesAsiaAmericasThesisBaseline, etc.) — they are referenced by the thesis narrative.
- Do not change the signature of `findReroute` in a breaking way. The new fields on RerouteResult are additive. Existing callers (TransportationMap, tracking-reroute-insight) must keep compiling.

14. Success criteria

- Critical port closure at the destination does not produce a route that re-enters the closed port.
- Vietnam -> US with LA closed selects a believable alternative gateway (Seattle/Tacoma or Oakland/SF).
- The displayed reroute avoids all critical zones.
- The UI explains why the reroute was selected (reasons[] rendered).
- If no safe route exists, status is "no_safe_route" and the UI says so instead of drawing a bad route.
- Existing non-disrupted routes still produce identical waypoints to today (regression check on existing thesis demos).
- Existing disruptions without `type` still work (inferDisruptionType fallback).
- Existing exports (findReroute return shape, LOGISTICS_HUBS, DEMO_DISRUPTION, getThesisS1RerouteWaypoints) remain compatible.


15. Suggested thesis wording

"The routing module was extended from a pure shortest-path algorithm into a logistics-aware decision model. Dijkstra's algorithm remains the core search method, but edge weights are replaced by composite logistics scores that account for distance, disruption severity, disruption type, hub availability, transport mode, gateway suitability, and route validity. Critical disruptions remove unsafe hubs or edges from the graph, while lower-severity events add penalties. If the intended destination gateway is unavailable, the system evaluates alternative safe gateways and returns an explainable reroute decision."
