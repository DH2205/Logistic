\section{Conclusion}

This thesis presented the design and implementation of LogiShop, a web-based platform for international shipping and delivery management. The project was motivated by a practical industry problem: shipment volume and user data keep growing, while many operations still rely on fragmented systems that produce slow updates and inconsistent decisions.

LogiShop brings order management, shipment tracking, and route visualization into one workflow. Technically, the system shows that a \textbf{monolithic architecture} can support real logistics workflows without enterprise-scale infrastructure in the early stage. API route handlers, a structured data layer, and external carrier synchronization cut manual work and improve consistency.

The transportation map module is one of the more useful parts of the system. It is easier to read than traditional log-based tracking because users can see shipment routes and statuses on a map. The one-click refresh also saves time by updating order and shipment data in a single operation.

Another contribution is the disruption-aware routing framework. It is still a prototype, but it supports decisions by identifying possible route disruptions and recommending alternatives.

The thesis concludes that LogiShop meets its main goals. It supports shipment monitoring, improves workflow productivity, and provides a base for future logistics tools. It also stands as both a software artifact and an engineering case study.

\subsection{Future Work: Performance and Scalability}

LogiShop's monolithic architecture keeps operations efficient and cloud hosting cheap for Vietnamese SMEs, so future scaling will focus on the throughput of this single core rather than splitting it apart. To handle more transactions while keeping the monolith, the development roadmap includes several optimizations.

First, to improve data ingestion, the Supabase database layer will be tuned with better indexing, table partitioning for chronological tracking logs, and connection pooling, so the core instance can handle heavy concurrent reads and writes during peak hours.

Second, an in-memory cache (such as Redis) will be added to the monolith to store frequent carrier API responses and geospatial routing data. This reduces the load on the route-weighting engine and lowers API latency. With better indexing, query optimization, and local caching, the monolith can be scaled horizontally behind standard load balancers, letting LogiShop handle growing logistics workloads reliably and at low cost. \cite{harpreet2023overcoming} \cite{khedr2024enhancing}.
